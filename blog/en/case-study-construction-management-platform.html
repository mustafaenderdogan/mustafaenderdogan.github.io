Construction case study

A work management platform for construction and contracting firms

October 9, 2026 5 min read

In construction and contracting, information usually sits in spreadsheets, messaging groups and the site manager's notebook. Questions such as whether a subcontractor worker's safety certificate has expired, how much rebar is left at the Kartal site or what was paid for the same material last month all have answers, but finding them takes a chain of phone calls.

The Work Management Platform (İYP in Turkish) is a web application that brings that information into one system. This article explains what it does and why.

Scope

  • Subcontractor documents: subcontractor workers' documents and whether they're cleared to enter the site. Workers with missing documents are flagged on the timesheet.
  • Site stock: stock, material consumption and cost per site.
  • Quote comparison: a new quote is instantly compared with past purchase prices for the same material.
  • Field reports: reports from a tablet, with photos and location.

The scope is deliberately narrow. The platform is not meant to be an ERP that does everything; the aim is to do the four jobs that waste the most time on site, and to do them well.

Role-based screens

If a site manager and a board member see the same screen, both find it harder to do their jobs. So in the platform every user sees the screens for their own role. The demo has seven sample accounts: company administrator, HR and administration, two site managers responsible for different sites, purchasing and warehouse, field staff, and read-only management.

Field staff can enter reports on a tablet but can't edit them. A site manager sees only the sites they're responsible for. Purchasing manages stock, suppliers and quotes, and management sees read-only summaries. Permissions are enforced on the server, and some of the automated tests verify exactly that: a role can't use the API to reach data it can't see on screen, and one company's data stays isolated from another's.

Timesheets and Excel

On site, timesheets are usually kept in Excel and copied into payroll by hand at the end of the month. In the platform, the timesheet is a table for each project and month. You tap a cell to record the day (worked, leave, sick, overtime), or fill in today for everyone at once. HR approves and closes the month, and a closed month can only be reopened with a reason. At month end, payroll gets an Excel export.

Rather than ignore Excel, the platform works with it. Employee and material lists can be imported from a ready-made Excel template. You see a preview first, and invalid or duplicate rows are left out.

Data and security

Subcontractor and staff records include sensitive fields such as national ID numbers and IBANs. These fields are stored encrypted. Only an authorised user can reveal them on a person's record, and every reveal is logged. Two-factor authentication is available at login. When a data subject request comes in, the person's details, documents and timesheets, along with a record of who accessed their data, can be prepared as a single file. Because the data belongs to the company, the company administrator can export all of it as Excel and JSON at any time.

Automated tests

The platform has 138 API endpoints, and 269 automated tests run on every release. Having that many tests is a necessity, because in areas such as stock, cost and document compliance, the price of a bug is paid on site. Whenever a new feature is added, the tests check that existing calculations still hold, so making changes is nothing to be afraid of.

Why does the demo run in the browser?

The best way to explain business software is to let people use it. A demo can't use real data, though, and setting up a server for every visitor would be an unnecessary cost. So the platform demo (interface in Turkish) runs in the browser:

  • It uses the real interface, with an in-browser demo API in place of the server.
  • The data is entirely synthetic, with no real national ID numbers, IBANs or email addresses.
  • Each role logs in with one click and no password, and "Reset demo" puts everything back the way it was.
  • Any changes you make stay in your own browser.

This way the whole product can be tried out, even on static hosting.

Lessons from this project

  • Starting narrow works better. Picking the few jobs that waste the most time on site pays off sooner than a broad but half-finished system.
  • The design should start from the user's role, because a screen that shows everyone everything ends up helping no one.
  • Permissions have to be enforced on the server. Hiding something in the interface isn't security.
  • For calculations like cost and stock, write the tests from day one. Automated tests are the only safe way to grow the system.
